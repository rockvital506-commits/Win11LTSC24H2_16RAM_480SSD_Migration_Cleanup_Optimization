## Context

Stage 7 — финальный этап сборки: развернуть рабочий DevOps-контур (WSL2 + нативный Docker Engine + VMware Workstation Pro) и установить пакеты профиля. Спецификация (`anchor1.md`, блок Stage 7) задаёт последовательность, но четыре момента требуют решения:

1. **Поставка дистрибутива.** `anchor1.md` предписывает скачать `ubuntu.appx` через `curl`. Однако (а) AR-601 требует установки ПО только через winget, (б) `msstore` отключён (AR-604), (в) станция работает в режиме офлайн-носителя (README §5.7.3), (г) AR-709 запрещает скриптам самостоятельно выходить в сеть.
2. **Лимиты WSL2.** Значения `processors=4`, `memory=6GB`, `pageReporting=false` заданы исследованием; нужно закрепить, что шаблон `.wslconfig` — единственный источник (AR-703), иначе лимиты «расползутся» по скриптам.
3. **Контейнеры.** Docker Desktop нарушает принцип «без сторонних посредников» и тянет собственные обновления; AR-707 требует нативный Engine внутри дистрибутива с томами на `D:\Docker`.
4. **Границы с доменом `packages/`.** Часть инструментов (VMware, дистрибутив WSL2) не поставляется через winget; нужно явно разделить «Windows-ПО через winget» и «офлайн-компоненты с носителя».

Дополнительно требуется расширение allow-list `scripts/common/Guard.psm1` под рабочие каталоги Stage 7 (`C:\DevOps`, `D:\VM`, `D:\Docker`) — это изменение контура безопасности, поэтому фиксируется ADR.

## Decision

1. **Дистрибутив WSL2 — офлайн-компонент, а не Windows-приложение.** AR-601 (`winget-first`) распространяется на Windows-ПО; дистрибутив Linux поставляется пакетом с носителя `F:\WSL2\ubuntu.appx` (README §5.7.3) и не коммитится в Git (AR-804). Исключение фиксируется здесь и не расширяется.
2. **Два пути установки дистрибутива:** `AppxExe` (по умолчанию, как в `anchor1.md`: распаковка пакета как архива + запуск `<distro>.exe` для создания Linux-пользователя) и `Import` (`wsl --import` из `install.tar.gz`). Выбор фиксируется в отчёте; оба идемпотентны (повторный запуск при уже установленном дистрибутиве ничего не делает).
3. **Лимиты WSL2 — только из шаблона.** `devops/wsl/.wslconfig.template` (`processors=4`, `memory=6GB`, `pageReporting=false`) разворачивается в `%USERPROFILE%\.wslconfig`; изменение значений — только через ADR (AR-703). `pageReporting=false` выбран ради `SC_SSD_LONGEVITY` (устранение паразитного I/O), `swap` не задаётся — используется файл подкачки дистрибутива на `D:`.
4. **Docker — нативный Engine внутри дистрибутива** (`systemd=true`), без Docker Desktop (AR-707). Каталог данных фиксируется в `/etc/docker/daemon.json` как `/mnt/d/Docker`; логи ограничены (`max-size=10m`, `max-file=3`). Пользователь добавляется в группу `docker`.
5. **VMware — WHP API** (ADR-0002); директивы `.vmx` — из шаблона (PAT-22).
6. **Политика P+E — динамическая** (ADR-0010): маска вычисляется при каждом запуске `Get-PerformanceCoreMask.ps1`; скрипт **не применяет эвристику** при неопределённости (один класс ядер, расхождение с `coreinfo`) — выдаёт WARN и требует решения владельца (AR-906).
7. **Границы доменов:** Windows-ПО — `packages/` (winget, фиксация версий, lock-файл); офлайн-компоненты (дистрибутив WSL2, VMware Workstation Pro, Sysinternals `coreinfo`) — носитель `F:` + SHA256 в репозитории. Установка профиля — отдельный шаг с отчётом (AR-607).
8. **Окно сети — одно.** Stage 7 выполняется при открытом владельцем окне сети (стык Stage 6→7, README §4.5); ни один скрипт домена не поднимает и не опускает интерфейсы (AR-709). После завершения установки профиля окно закрывается владельцем, и станция возвращается в офлайн-режим.
9. **Расширение Guard.** Allow-list дополняется `C:\DevOps`, `D:\VM`, `D:\Docker` (ADR-0016); остальные корни и предохранитель самоблокировки AR-506 не меняются.

## Consequences

**Положительные:**

- Контур воспроизводим без интернета: дистрибутив и VMware — с носителя, версии зафиксированы, хэши проверяемы.
- Единый источник лимитов WSL2 и директив ВМ исключает дрейф конфигурации.
- Нативный Docker без Docker Desktop: нет стороннего демона-посредника, тома на `D:` (износ SSD и ёмкость `C:` под контролем).
- P+E-политика безопасна по построению: при неопределённости маска не применяется.

**Отрицательные / компромиссы:**

- Исключение из AR-601 для дистрибутива WSL2 — осознанное сужение правила; при появлении официального winget-пакета `.wsl`/дистрибутива решение пересматривается.
- `-ApplyPowerPlan` меняет схему питания хоста; применяется только явным флагом (AR-204).
- Docker Engine ставится из apt-репозитория без пофайлового хэш-пиннинга: версия фиксируется в отчёте по факту установки (открытый пункт `S7-OPEN-2`).

**Нейтральные:**

- Образы контейнеров фиксируются тегами версий; плавающий `latest` для dev-стека не используется.

## Alternatives

| Вариант | Причина отклонения |
|---|---|
| Скачивание дистрибутива скриптом (как в `anchor1.md`) | Нарушает AR-709 и офлайн-парадигму; канал загрузки — точка атаки |
| `wsl --install -d Ubuntu` (онлайн) | Требует msstore/интернет-источника (AR-604) |
| Docker Desktop | Сторонний демон-посредник, автообновления, лицензия; нарушает AR-707 |
| Тома Docker на `C:` | Износ системного SSD и риск переполнения `C:` (SC_SSD_LONGEVITY) |
| Хардкод маски P-ядер | Прямой запрет AR-704 |
| Установка всего ПО вручную | AR-601/AR-602: без фиксации версий и lock-файла нет воспроизводимости |
