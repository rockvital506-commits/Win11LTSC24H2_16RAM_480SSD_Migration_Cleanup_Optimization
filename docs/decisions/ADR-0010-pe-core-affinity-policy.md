## Context

Аппаратная платформа — Intel Core i7 с **6 Performance + 8 Efficiency** ядрами (Thread Director). В `docs/research/anchor1.md` зафиксировано, что отключение VBS/HVCI/LSA возвращает планировщику хоста прямой доступ к Thread Director и позволяет удерживать потоки компиляции на P-ядрах.

Правило AR-704 запрещает хардкод маски P-ядер, но требует зафиксировать метод их определения в ADR. Это тот случай, когда §4.1 `GATE_AMBIGUITY` (более двух вариантов) требует явного решения, а не «угадывания» агентом.

Рассматриваемые подходы:

| Подход | Суть | Ограничения |
|---|---|---|
| A. `GetLogicalProcessorInformationEx` (RelationProcessorCore) + `EfficiencyClass` | Канонический Win32 API; `EfficiencyClass` — официальный признак P/E у гибридных CPU | Требует P/Invoke из PowerShell 5.1; поля зависят от версии структуры |
| B. `Get-CimInstance Win32_Processor` (NumberOfCores/NumberOfLogicalProcessors) | Простой WMI-запрос | **Не различает** P и E ядра — только общее число |
| C. Sysinternals `coreinfo -c` | Готовая утилита, наглядный вывод | Внешний бинарник (лицензия Sysinternals), парсинг локализованного вывода |
| D. Ручная фиксация маски (хардкод) | Максимально просто | Нарушает AR-704; ломается при изменении микрокода/BIOS/гипервизорного режима |

## Decision

Принят комбинированный метод:

1. **Основной источник — подход A:** P/Invoke `GetLogicalProcessorInformationEx(RelationProcessorCore, …)` с чтением поля `EfficiencyClass`; ядра с более высоким значением `EfficiencyClass` — P-ядра, с низким — E-ядра.
2. **Перекрёстная проверка — подход C:** при наличии Sysinternals `coreinfo` вывод `-c` используется как контрольный (количество ядер P/E должно совпасть с ожидаемым 6P+8E).
3. **Запрещённые опоры:** подход B — недостаточен (не различает типы ядер), используется только как санитарная проверка общего числа логических процессоров; подход D — запрещён к применению.
4. **Динамика:** маски вычисляются **на каждой загрузке** (скрипт `devops/cpu-policy/Get-PerformanceCoreMask.ps1`), результаты не переносятся между загрузками и не хардкодятся ни в одном файле.
5. **Политика привязки (AR-705):** тяжёлые сборки/тесты, `vmmemWSL` и процессы компиляторов привязываются к P-ядрам с приоритетом **не выше `Normal`**; фоновые процессы (индексация, служебные задачи) смещаются на E-ядра.
6. **Предусловие результативности:** VBS/HVCI/LSA отключены и не восстанавливаются (`SC_VBS_HVCI_DISABLED`, AR-706, `GATE_IMMUTABLE`). При включённых VBS/HVCI политика не применяется — сначала устраняется нарушение.
7. **Границы вмешательства:** ADR-0010 регулирует **планирование нагрузок** и **не изменяет** BCD, `hypervisorlaunchtype`, `bcdedit`-флаги или схему питания ядра в части §1.4 (README §2.3, AR-504). `power-plan.json` описывает только параметры схемы питания, не относящиеся к запрещённым мутациям.
8. **Разделение с ADR-0002:** ADR-0002 (VMware через WHP) отвечает за сосуществование гипервизоров; ADR-0010 — только за привязку нагрузок к ядрам. Пересечение запрещено.

## Consequences

**Положительные:**

- Политика переносима между BIOS-версиями и не ломается при изменении порядка нумерации логических процессоров.
- Интерактивность хоста сохраняется: тяжёлые задачи не конкурируют с UI за E-ядра.
- Отсутствие хардкода удовлетворяет AR-704 и упрощает аудит.

**Отрицательные / компромиссы:**

- P/Invoke-код требует аккуратной обработки `ERROR_INSUFFICIENT_BUFFER` (двухпроходный вызов) и проверки версии структуры.
- Корректность `EfficiencyClass` зависит от микрокода Intel; при расхождении с `coreinfo` приоритет отдаётся `EfficiencyClass`, расхождение фиксируется в отчёте Stage 7.

**Нейтральные:**

- Приоритет не выше `Normal` означает, что политика не «выжимает» систему в ущерб стабильности (SC_CORE_STABILITY).

## Alternatives

| Вариант | Причина отклонения |
|---|---|
| B — только WMI | Не различает P/E-ядра; непригоден как основа |
| C — только coreinfo | Внешний бинарник и парсинг вывода; зависимость от сторонней утилиты и локали |
| D — хардкод маски | Прямое нарушение AR-704; риск при изменении конфигурации |

## Verification

- `Get-PerformanceCoreMask.ps1 -Audit` выводит: число P/E-ядер, маски в шестнадцатеричном виде, источник данных, результат сверки.
- Критерий приёмки на железе (Stage 7): результат `P=6, E=8` и совпадение с `coreinfo -c`; расхождение — стоп и запрос по `GATE_AMBIGUITY`.
- Проверка отсутствия хардкода: валидатор ищет в домене `devops/` литеральные маски (эвристика `0x…`) вне манифестов.
